# 리뷰 체크리스트

PR 전에 AI가 스스로 검수하는 기준입니다 (1인 운영이라 사람 리뷰어 대신 이 표가 리뷰를 맡음). 이 저장소에서 실제로 난 버그 유형을 항목으로 둡니다.

## 판정

| 판정 | 쓰는 법 |
| --- | --- |
| 통과 | 근거(파일·라인, 실행한 명령과 결과)를 함께 적습니다 |
| 미통과 | 위치와 이유를 적습니다 |
| 해당 없음 | 이유를 한 줄로 적습니다 |
| 미확인 | 확인하지 못한 항목입니다. **통과로 바꾸지 않습니다** |

A·F·G는 항상 적용하고, 나머지는 해당 변경이 있을 때 적용합니다.

## A. 범위

| 확인 | 방법 |
| --- | --- |
| 요청 범위 밖 파일 변경이 없는가 | `git diff --stat <base>...HEAD` |
| 커밋·PR 하나에 목적이 하나인가 | `git log --oneline <base>..HEAD` |
| 제목이 `type: 요약` 형식인가 | [CONTRIBUTING.md](../../CONTRIBUTING.md) > 2 |

## B. 멀티팀·권한 (데이터 접근을 바꿀 때)

| 확인 | 방법 |
| --- | --- |
| 모든 조회·쓰기가 `team_id`로 범위를 좁히는가 | 쿼리마다 `.eq("team_id", ...)` 확인 |
| 사용자 판정이 활성 멤버십 기준인가 (`players.status`만 보지 않음) | [ADR: 팀 사용자 판정 기준](../adr/팀-사용자-판정-기준.md) |
| 화면의 제한(`canWrite`·viewer)이 서버(RLS·Route Handler)에도 있는가 | UI 조건 ↔ 정책·라우트 대조 |
| 팀을 전환해도 이전 팀 데이터가 남지 않는가 | queryKey 에 `teamId` 포함 여부 |

## C. DB·RLS·RPC (`db/`를 바꿀 때)

| 확인 | 방법 |
| --- | --- |
| 새 번호 파일인가, 번호가 겹치지 않는가 | `ls db \| sort` — 적용된 파일은 수정하지 않음 |
| 새 테이블에 RLS 와 팀 정책이 있는가 | `enable row level security` + 정책 |
| `insert/upsert ... select` 에 SELECT 정책, `upsert` 에 UPDATE 정책이 있는가 | 정책 목록 대조 |
| 함수 권한을 명시했는가 (`grant`/`revoke execute`) | 클라이언트가 부르는 RPC 는 `authenticated` 실행 권한 필요 |
| 클라이언트 `.rpc()` 인자 이름이 최종 함수 시그니처와 같은가 | 인자명이 다르면 PGRST202 |
| `when others` 로 오류를 숨기지 않는가 | 최소한 `sqlstate` 를 반환 |
| PR에 적용 순서와 롤백 방법이 있는가 | PR > 영향 범위 |

## D. Supabase 호출 (클라이언트·Route Handler)

| 확인 | 방법 |
| --- | --- |
| `upsert(..., { ignoreDuplicates: true }).select()` 로 기존 행을 기대하지 않는가 | 기존 행은 반환되지 않음 — 따로 조회 |
| 0행 갱신을 성공으로 처리하지 않는가 | RLS 차단은 오류 없이 0행 |
| 실패 메시지에 오류 코드가 보이는가 | `describeDbError` (`src/shared/utils/dbError.ts`) |
| Route Handler 의 클라이언트 선택이 맞는가 | 사용자 권한 검사 후에만 service client |

## E. 서버 게이트·외부 연동

| 확인 | 방법 |
| --- | --- |
| 서버가 403 을 주는 조건(TOTP 등)에서 화면이 먼저 호출하지 않는가 | 게이트 조건 ↔ 호출 시점 대조, 403 은 잠금 상태로 처리 |
| 값을 못 불러온 상태에서 저장해도 기존 값을 지우지 않는가 | 저장 payload 확인 |
| 연동 미설정과 연동 실패를 구분하는가 (캘린더·Google Chat) | 미설정은 실패로 알리지 않음 |
| 날짜·주차 비교가 KST 기준인가 | `toSeoulYmd` 사용 여부 |

## F. 보안

| 확인 | 방법 |
| --- | --- |
| 비밀값이 코드·로그·문서·PR에 없는가 | `git grep -nE "service_role\|secret=\|ghp_\|github_pat_\|BEGIN .*PRIVATE KEY"` |
| 서버 전용 키를 클라이언트에 노출하지 않는가 | `NEXT_PUBLIC_*` 외 키가 클라이언트 import 경로에 없음 |

## G. 검증과 산출물

| 확인 | 방법 |
| --- | --- |
| `npm run check` 를 실제로 실행했는가 | 실행 결과를 그대로 기록 |
| 화면을 직접 보지 않았으면 "확인 필요: <경로>"로 남겼는가 | PR > 검증 |
| 구현됐다고 쓴 내용을 코드에서 확인했는가 (PR 설명·추측이 아님) | 해당 파일 직접 열람 |
| 모르는 값(이슈 번호·날짜·운영 DB 상태)을 추측으로 채우지 않았는가 | 빈칸 확인 |
| "필요하면", "적절히"처럼 사람마다 다르게 읽히는 표현이 없는가 | 문장 검토 |
