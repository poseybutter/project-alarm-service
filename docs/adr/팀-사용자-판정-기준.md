# 팀 안의 사용자 판정은 활성 멤버십 기준

## 상태

적용 중 — `db/V68_membership_identity_basis.sql`

## 맥락

멀티팀 전환 후 "이 사용자가 이 팀의 활성 구성원인가"를 두 곳에서 따로 판정한다.

- 팀 접근·RLS·team-context: `team_memberships.status = 'active'` + `profiles.account_status = 'active'`
- 출석·업무 상태 변경·퀘스트 완료 RPC: 그 팀 `players` 행의 `status = 'active'`

두 상태가 어긋나는 경로가 있다 (players 행 없이 만든 과거 멤버십, 기본 소속 변경 시 players 를 정지하는 V45 트리거, 비기본 멤버십 상태가 players 로 전파되지 않음).
그 결과 팀 화면은 보이는데 출석·상태 변경만 실패하는 사용자가 생긴다.

## 결정

- 팀 안의 사용자 판정 원본은 **활성 멤버십**이다: `team_memberships.status = 'active'` 이고 `profiles.account_status = 'active'`.
- `players` 는 팀별 점수·표시용 저장소로만 쓴다. 멤버십의 `legacy_player_id` 로 찾아가며, `players.status` 로 권한을 판정하지 않는다.
- 활성 멤버십에는 같은 팀 `players` 행이 반드시 연결된다. 연결이 없으면 데이터 결함으로 보고 보정한다.

## 기각한 대안

- **`players.status` 동기화 강화**: 판정 원본이 두 개로 남아 트리거가 하나만 빠져도 다시 어긋난다.

## 결과

- 출석·업무 상태·퀘스트 완료 RPC 는 `app_my_player_id()`(V68)로 본인을 판정한다.
- [단계적 DB 정규화](단계적-DB-정규화.md)의 "legacy `players` 가 권위" 원칙은 점수 저장에만 남고, 사용자 판정에는 적용하지 않는다.

## 다시 볼 조건

- `players` 테이블을 제거하거나 점수 저장소를 멤버십으로 옮길 때.
